# Review round 1: network-failure-diagnostics

Verdict: **APPROVED** (no blockers, no majors; three minors, all optional).

Gate (run by the reviewer in WSL): `make check VENV=~/.venvs/gmail-mcp` exits 0, 468 passed, coverage 99.23%. No `requirements*.txt` or dependency change (git status clean for them).

## Requirement verification

- R1: `gmail_client.py:143-149`, `netcheck.is_dns_failure`. The DNS branch is the first statement inside the final `except (GoogleAuthError, HttpLib2Error, OSError, TimeoutError)` clause. It follows the `AuthRequiredError`, `RefreshError` and `HttpError` clauses, so it cannot swallow them. `_clear_rejection` is only on the success path and `_record_rejection` only in the unchanged RefreshError/HttpError branches; rejection semantics are unchanged (a test asserts `rejected_at is None` after a DNS failure). The raise uses `from None`. Tests cover ServerNotFoundError, a TransportError built the library's way, TransportError with `__cause__=gaierror`, a bare gaierror, and negatives (HttpLib2Error, TimeoutError, OSError(ECONNRESET), TransportError("x")).
- (1) Real shapes: installed `google_auth_httplib2` does `except (HttpLib2Error, HTTPException) as exc: raise TransportError(exc)`. That yields `__context__ = exc` and `args = (exc,)`, and `is_dns_failure` walks `__cause__`, `__context__` and `args`, so it is detected. The test helper mirrors this shape exactly. The walk is a BFS bounded to 8 distinct exceptions, with a seen-id set (cycle-safe). `gaierror` is an `OSError`, so a bare one reaches the branch. Negatives are correct. Note: the spec said "`__cause__`/`__context__`", and the implementation adds `args` as well. That is a harmless superset, and it is needed for robustness.
- R2: message is fixed, starts with `NETWORK_UNREACHABLE:`, is about 260 chars, and contains no URL, host name, query, token or path (it names only `scripts/restart.*` and `scripts/logs.*`). It says "This may be temporary", so it does not claim permanence. It goes through the existing `GmailMcpError.user_message` handling; `test_server.py` asserts the client-visible text through a real `Client`.
- R3 and (4): `AuthStatus.network` is added and the model stays frozen. `compute_auth_status` is still sync and pure, with `network: NetworkState = "ok"` as a defaulted last parameter, so existing callers are unaffected. `ready_to_retry = signed_in and network == "ok"` (D4). For `dns_failure`, `next_step` is `DNS_NEXT_STEP` when signed in and is prefixed to the token text otherwise. A warning is added. `rejected_at` and the other fields are untouched.
- R4 and (5): `probe_network` (`server.py:131`) calls `resolve_hosts(PROBE_HOSTS, timeout=2.0)`, catches everything, and a timeout yields `dns_failure`. `_auth_status_now` is used by BOTH the tool (via `asyncio.to_thread`) and the resource. The sync resource handler is run by the SDK in a worker thread (`FunctionResource.read` uses `anyio.to_thread.run_sync` for non-async fns, verified in the installed SDK), so neither the tool nor the resource blocks the event loop. Worst case is about 2 s of added latency. A hung `getaddrinfo` thread is abandoned, not cancelled (`shutdown(wait=False, cancel_futures=True)`), as the spec acknowledges; a probe per call can accumulate lingering threads only while the resolver hangs, which is acceptable and bounded by the call rate.
- R5: the tool description, the `gmail://auth/status` description and the `gmail://guide/auth` text are updated. `auth_required_message` is unchanged. Tests assert the text.
- R6 and (9): README (tool table, payload fields, triage section), `docs/SPEC.md` (tool row plus the NETWORK_UNREACHABLE paragraph), `CLAUDE.md` (auth_state line, lineage line) and CHANGELOG are consistent with the code. A grep for stale "never contacts Google", "pure/no network" and "does no I/O" found no stale claim outside the intentionally amended sentences (the `auth_state.py` module docstring still says "never contacts Google", which remains true, and was amended to say the probe is injected). The only inconsistency is minor item m2 below.
- R7 and (7): tool set and order, four resources, guards and routes are untouched. The existing tool-set and resource-set tests pass without edits.
- (6) Tests: the conftest autouse fixture patches `gmail_mcp.server.resolve_hosts` with a healthy stub. It does not mask logic under test, because `probe_network` and `compute_auth_status` still run; tests that need real probe behaviour re-patch `resolve_hosts` and `socket.getaddrinfo`. `test_netcheck.py` patches `socket.getaddrinfo` itself, so nothing touches the network. The hung-resolver test uses a 0.2 s cap and an event to release the thread. Tests are meaningful (shape fidelity, cycle, log content, frozen model, tool/resource agreement, restart text).
- (8) Logs: `gmail dns failure` carries only `outcome` and `cause` (a class name). A test asserts the host name is absent from logs.

## Flagged points

- (a) `cause` field: it records the top-level caught class (for example `TransportError`), not the root. Recommendation: **keep**. The spec said "cause: <class name>", the top-level class is what the existing transport log records as `outcome`, and it is content-free. The info loss is small: `outcome=dns_failure` already names the root class of interest. Optionally record the matched root class name (`ServerNotFoundError` or `gaierror`) in a follow-up; not required.
- (b) `netcheck.py` imports `httplib2`; `healthcheck.py` imports `netcheck`. Verified in the venv: `import gmail_mcp.healthcheck` leaves `gmail_mcp.config` out of `sys.modules`, so the healthcheck still never loads Settings or the environment secrets. `httplib2` is already a pinned runtime dependency of the image (google-api-python-client), so the import is harmless and adds some ms of start-up per healthcheck run (every 30 s; the 5 s timeout is ample). Spec A text that says "stdlib only" would be slightly inaccurate; a one-line note in `docs/specs/container-dns-resilience/SPEC.md` (or accepting the module docstring, which already says "Stdlib plus httplib2") is enough.
- (c) Closed-file `ValueError` traceback: this is a test-isolation defect that is pre-existing, not a product defect. `tests/test_logging.py::test_configure_logging_installs_single_json_handler` calls `configure_logging("INFO")`, which installs a root `StreamHandler(sys.stdout)` (`logging_setup.py:88`) bound to pytest's captured stdout, and never removes it. Once that capture file is closed, any later log record at or above the root level hits a closed stream and Python's logging prints "--- Logging error ---" with `ValueError: I/O operation on closed file`. The new `test_network_unreachable_is_a_clear_tool_error` makes the mcp SDK log the tool error, and it is the first later test that logs on that path. Order-dependent: the full gate run by the reviewer showed no traceback, and the targeted run did not either. Classified **minor**, since it does not affect results or the exit code.

## Issues

- **m1 (minor, tests/test_logging.py:84-90):** the test leaks a root handler. Suggested fix: restore `logging.getLogger().handlers` (and level) in a fixture or `try/finally` / `monkeypatch`, so later tests do not inherit a handler bound to a closed capture stream. Outside the strict scope of this spec (pre-existing); fix or accept with justification.
- **m2 (minor, src/gmail_mcp/netcheck.py:1 and CHANGELOG.md):** the first docstring line still says "(stdlib only)" and the CHANGELOG says "stdlib DNS probe", while the module now imports `httplib2`. Suggested fix: change both to "stdlib plus httplib2", and add the one-line note to Spec A.
- **m3 (minor, src/gmail_mcp/auth_state.py:2-5):** the docstring "Pure by design ... never contacts Google" is still true, but it would be clearer to state that `compute_auth_status` receives the DNS result from `server.py`. It already says this in the next sentence; no action required beyond optional wording.

No deviations from the spec and nothing outside the spec was added.
