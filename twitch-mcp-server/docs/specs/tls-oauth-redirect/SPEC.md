## 1. Problem / motivation

Twitch's developer console rejects any non-HTTPS OAuth Redirect URL — *"Redirect URIs must use HTTPS
protocol"* — so the redirect URI this server derives (`config.py:282`, hardcoded
`http://127.0.0.1:{HOST_PORT}/oauth/callback`) can never be registered. Consequence: `TWITCH_USER_OAUTH`
cannot be completed at all, which blocks the 7 user-token read tools, both account tools, and all 16
write tools. The server is unusable beyond app-token mode on any account where the console enforces this.

Twitch's own documentation still shows `http://localhost:3000`, so the console is stricter than the
contract. This spec follows the console, because the console is what has to be satisfied.

## 2. Goals

- A redirect URI that the Twitch console accepts and that this server sends byte-for-byte identically.
- The server terminates TLS itself, still bound to host loopback only.
- App-token mode (the default 16 reads) is untouched when TLS is not configured.
- No third-party tunnel, no public exposure, no new container.

## 3. Non-goals

Public-interface serving, ACME/Let's Encrypt, HTTP/2, mutual TLS, client certificates, EventSub,
changing the published port, and any change to the Helix client (it already speaks HTTPS to Twitch).

## 4. Decisions

| Ref | Decision | Rationale |
|---|---|---|
| **T-D1** | TLS is terminated **inside the existing container** by uvicorn (`ssl_certfile`/`ssl_keyfile`), not by a sidecar proxy. | Keeps one container, one entry point, and the current Dockerfile posture (read-only rootfs, dropped caps). A Caddy/nginx sidecar adds a second privileged-ish process for no benefit at loopback. |
| **T-D2** | TLS is **opt-in**: `TWITCH_TLS_CERT_FILE` + `TWITCH_TLS_KEY_FILE`. Both unset → today's plain-HTTP behaviour, unchanged. | The 16 app-token reads need no OAuth and no TLS; forcing TLS would break working installs and churn the whole test suite for no gain. |
| **T-D3** | The `redirect_uri` and `sign_in_url` **scheme is derived from TLS mode** — `https` when a cert is configured, `http` otherwise. | OAuth compares the registered URI against the sent one exactly, so the two must never be able to disagree. |
| **T-D4** | Certificate is a **self-signed leaf plus a local CA**, generated by a bundled `scripts/make-cert.sh` (openssl), and the CA is imported into the **current user's** Windows trust store (`certutil -addstore -user Root`). No `mkcert` dependency; no admin rights. | Without a trusted CA the browser interstitials the callback and the operator has to click through a security warning to finish a sign-in. A user-store CA removes the warning without a machine-wide trust change. |
| **T-D5** | Leaf identity: `CN=localhost`, SAN `DNS:localhost, IP:127.0.0.1`. 398-day leaf validity, 10-year CA. | Chrome/Edge require a SAN, and 127.0.0.1 must be an IP SAN because the registered URI uses the literal address, not the hostname. |
| **T-D6** | Registered URI is **`https://127.0.0.1:8770/oauth/callback`**; `HOST_PORT` still defaults to 8770 and the container port stays 8000. | Keeps compose, the healthcheck and every sibling server's port convention intact. |
| **T-D7** | Cert and key are mounted **read-only** at `/certs`, and the key must be mode **0600** or startup refuses. | Matches the token-file discipline (R48). A world-readable private key on a shared host is the one way this feature can leak. |
| **T-D8** | `/healthz` stays unauthenticated; the healthcheck and `scripts/status.sh` / `smoke.sh` switch scheme with TLS mode and disable certificate verification for the loopback probe only. | `urllib` under a self-signed CA would otherwise fail the container healthcheck. Verification-off is confined to the self-probe, never to Twitch calls. |
| **T-D9** | When TLS is on, `http://` requests to the same port are **rejected, not redirected**. | A redirect would leak the bearer token in the `Authorization` header to a plaintext URL. Refusal is the safe default. |
| **T-D10** | *(amended 2026-10-30, approved by the human)* The `0600` key rule is enforced only where the filesystem can express Unix modes. `config.py` writes a probe file next to the key, chmods it to `0600` and reads it back: if the filesystem cannot hold that, the rule is skipped. If the probe cannot be written at all (the container's read-only `/certs`), the rule is skipped too — only a positive demonstration that modes are real may refuse a boot. | A Windows drive under WSL/drvfs reports `0777` for every file regardless of `chmod`, so a literal `0600` check makes TLS unreachable on the operator's own machine while protecting nothing: on NTFS the ACL is the actual control. ext4, xfs and APFS all pass the probe, so the rule still binds on Linux and macOS. Deciding from a probe is evidence about the filesystem, not an assumption about the platform. |
| **T-D11** | *(amended 2026-10-30, approved by the human)* The user-scoped trust step is documented for both non-container hosts: `certutil -addstore -user Root certs\ca.crt` on Windows, and `security add-trusted-cert -k ~/Library/Keychains/login.keychain-db certs/ca.crt` on macOS (login keychain, no administrator rights). `scripts/make-cert.sh` prints whichever applies. | Without a trusted CA the browser interstitials the callback on any platform; the point of the feature is that the operator never clicks through a security warning. macOS support is documentation and script output only — it is not testable from this Windows host and is not tested here. |

## 5. Requirements

- **T1** — `TWITCH_TLS_CERT_FILE` and `TWITCH_TLS_KEY_FILE` are read by `config.py` only (R6) and are either both set or both unset; one alone aborts startup naming the field, never the value (R7).
- **T2** — With neither set, every observable behaviour is exactly as today: plain HTTP, `redirect_uri` = `http://127.0.0.1:<port>/oauth/callback`, all existing tests pass unmodified.
- **T3** — With both set, uvicorn serves TLS on the same container port and `redirect_uri` / `sign_in_url` become `https://127.0.0.1:<port>/...`.
- **T4** — Startup refuses with a secret-free message when a configured cert or key path is missing, unreadable, not
  PEM, or when the key's mode is not `0600`. The mode rule is enforced wherever the filesystem can express `0600`, and
  skipped only where a probe file written next to the key proves that it cannot (T-D10) — a Windows drive mounted
  into WSL reports `0777` for every file, so refusing there would block TLS while protecting nothing.
- **T5** — The cert and key are refused if they sit inside the repo tree, so a key cannot be committed by accident.
- **T6** — `GET /healthz` requires no bearer and reports `tls: true|false` alongside the existing keys; every other route still requires the bearer (R3/R4).
- **T7** — The Host/Origin allowlist (R5), bearer auth (R4), and the single-`httpx`-module rule (R11) are unchanged; the Helix client still uses TLS to Twitch independently of this setting.
- **T8** — Plaintext requests to a TLS-enabled server are refused with a clear message and are **never** answered with a 3xx redirect.
- **T9** — Neither the certificate contents, the key contents, nor the key path appear in any log line, error message, or `/healthz` body (R52).
- **T10** — `scripts/make-cert.sh` (with a PowerShell twin) generates CA + leaf into a git-ignored `./certs`, prints only the CA path and fingerprint, and never prints key material.
- **T11** — The compose file mounts `./certs:/certs:ro` only when TLS is configured; the rootfs stays read-only and `/certs` is never writable.
- **T12** — `README.md` states the exact URI to register, matching the TLS mode, and the certificate-trust steps.

## 7. Security and invariants

Loopback-only binding (R1/R2), bearer-on-every-route-but-healthz (R4), Host/Origin guard (R5), the
default-deny allowlist (R25–R27), the write kill switches (R28) and "writes never retry" (R16) are all
preserved unchanged. This change **adds** transport security; it removes none. Specifics: private key
mode-0600 enforced wherever the filesystem can express a mode, and verified-not-skipped by a probe written
beside the key (T4/T-D10), plus a read-only mount (T11); no key material in logs (T9); no plaintext fallback
that could downgrade a bearer-bearing request (T8); certificate trust is user-scoped, not machine-wide, on both
Windows and macOS (T-D4, T-D11). Verification-disabled is confined to the container's own healthcheck probe.

## 8. Test plan and acceptance

`make check` stays green (ruff, `mypy --strict` over `src` and `tests`, ≥90% branch coverage). New tests
generate throwaway CA + leaf with `cryptography` into `tmp_path` so no test touches the operator's certs.
The `0600` rule gets both directions: a key at `0644` on a filesystem that can hold `0600` is refused, and the
same key is accepted when the probe reports that the filesystem cannot hold it — with the probe itself tested
in all three of its answers (modes real, `chmod` a no-op, folder not writable). macOS is documentation and
script output only (T-D11); it is not exercised from a Windows host.
Acceptance: **H1** `make check` passes. **H2** With TLS off, every pre-existing test still passes; the only
amendments to the existing suite are the three `/healthz` key-set assertions, which T6 itself requires (the body
gains a key, so "exactly four keys" becomes "exactly five").
**H3** With TLS on, `curl -k https://127.0.0.1:8770/healthz` answers and `/tools` without a bearer is 401.
**H4** The registered URI and the URI sent to `id.twitch.tv` are identical strings (unit-pinned).
**H5** Live sign-in completes in a browser with no certificate warning (operator-run, UNVERIFIED by default
per A1-D5/A2-D5).

## 9. Out of scope

Public exposure, ACME, HTTP/2, mTLS, pinning, HSTS, certificate rotation automation, EventSub, and any
change to the Helix client's transport.
